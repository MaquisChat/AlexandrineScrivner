# 0003. The session folder format

- **Status:** Accepted
- **Date:** 2026-11-24

## Context

The recorder and the research workbench are separate projects that meet at one thing: a folder on disk holding one session. The recorder writes it on the phone; the workbench reads it on the Mac, possibly years later and possibly with a newer version of either side. Neither project can call the other's code, so the folder itself has to carry the whole agreement.

The design spec (section 6) describes the folder. This record fixes the choices that were open when the format was first built and checked.

## Decision

1. **The schema file defines the shape; a short list of rules covers the rest.** `format/field-session.v1.schema.json` defines which keys `session.json` has and what each value looks like. The Swift reader in `Core/` mirrors it and is strict in the same way: unknown keys, wrong types and badly formed values are refused, with the place in the file named. The rules a schema cannot express (ids all different, every `spanId` real, only the last span open, a finished session closed and hashed) are written out in `format/README.md` and checked by the recorder. The two sides are kept in step by files both must accept (a worked example, and two more written by the recorder that use every key) and a set of broken copies both must reject.

2. **We write `session.json` ourselves, in a fixed order.** The file is produced by our own writer, not the system's general one, with keys in reading order (what the session is, then the recording spans, then the items on the page). The same session gives the same bytes on every platform, so the file can be compared byte for byte in tests, and a change between two saves shows up as a small, readable difference.

3. **Absent values are left out.** A value that is not known is not written at all; the file never says `null`. A reader can tell "not recorded" from "recorded as empty".

4. **One audio file per unbroken stretch of recording.** Each stretch, called a span, has its own audio file. A pause, an interruption or a crash ends a span and the next recording starts a new one. Positions on the audio are therefore always counted from the start of one continuous file, with no gaps to account for.

5. **Every item carries both a time and a place on the audio.** Each note, photo, clip and marker has the instant it was made (in UTC, with the phone's offset from UTC at that moment) and, when recording was running, which span it falls on and how many milliseconds into that span's audio. The position on the audio comes from the audio's own clock, not the wall clock, so it stays right if the phone's time is changed mid-session. Each stroke of handwriting carries the same, with its own span, because a handwriting block can run on across a pause.

   **A position is never past the end of its audio.** If the app is cut off, the last moments of audio can be lost while notes typed in those moments survive. When the span is closed, anything placed after the end of the audio that was kept is moved to the end; its own time is left alone. If the audio's length cannot be read at all, the span is taken to be as long as the last thing placed on it.

6. **Checksums are filled in when a session is finished.** While a session is being recorded, media files are still growing and have no checksum. Finishing the session computes a SHA-256 for every media file and writes it into `session.json`. A finished session can be checked for damage or missing files after any copy.

7. **Media files are named by kind and number.** `audio/audio-001.m4a`, `photos/photo-0001.heic`, `video/clip-0001.mov`, `ink/ink-0001.png`. The names carry no meaning beyond order; everything a reader needs is in `session.json`. The folder itself is named with the local start time, the title and the last four characters of the session's id.

## Consequences

- A change to the format means changing the schema, the Swift reader and writer, and the worked example together. Because both readers refuse keys they do not know, any change to what the file may contain, even one new optional key, is a new `version` number. Until the first version of the app is in use, version 1 is still being settled and is changed in place.
- After a crash, a photo, clip or handwriting block whose file never reached the disk is removed from the session, and a span with no audio file is removed, leaving its notes with their times but no place on the audio. The app tells the owner what was dropped.
- `session.json` is never replaced by a version the reader could not read back. The save is refused instead and the last good copy stays.
- The worked example in `format/examples/` is generated by the recorder's own code and compared byte for byte in the tests, so the code and the published example cannot drift apart unnoticed.
- The workbench can build its importer against the schema and the example without waiting for the app.
- The example's media are small real files (a tone, flat colours, a test pattern) carrying the same times and places inside them that an iPhone's camera writes. A session checker, `scrivner-check`, verifies a folder: the manifest, every file and checksum, and that what each media file says about itself agrees with `session.json`. It runs on the example in the automatic checks, and on real folders from the phone with `tools/mac-check-session.sh`.
- Writing the file ourselves means we own a small JSON writer and reader. They are covered by their own tests.
- Numbers 0001 and 0002 are reserved for the two decisions that come out of the stage 0 device tests (how the session audio is kept alive, and how video clips get their sound).
